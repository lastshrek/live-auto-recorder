# 直播自动录制（抖音版）

监控一批主播，开播就自动录下来。核心是「直拷录制 + 崩溃可恢复 + 不误删已有产物」——
一个无人值守跑着的录制工具，最怕的不是录不到，而是录完了发现文件坏了、或者被自己搞丢了。

默认按**原画**录制；想省硬盘可以切到**最低画质**，画质由你定。

## 它能做什么

- **多主播并发监控**：轮询发现开播，按画质偏好选档，直接 `-c copy` 拉流——不转码，所以
  选定哪档就原样保存哪档，不会二次压缩损失画质，CPU 占用也很低
- **断流自动续录**：断流/超时自动换新分片，重连后续上，最后合并回一个文件
- **完整性校验**：录完解码验证，通过才替换/删除源文件；校验失败优先保留原件
- **崩溃可恢复**：断电、强杀、崩溃后重启，未完成的任务接着做，不用从头再来
- **超大文件拆分**：超过 15.5 GB（十进制）的成片按关键帧拆成上传分段，原文件归档保留

## 平台支持

Windows / macOS 双平台。**核心录制链路在两端完全一致**，只有系统级配套能力有差异，
缺失的能力会自动降级，不会导致应用无法运行。

| 能力 | Windows | macOS |
|---|---|---|
| 录制、转封装、合并、上传拆分、完整性校验 | 支持 | 支持 |
| 托盘常驻 / 关闭窗口继续录制 | 支持 | 支持（菜单栏图标） |
| 开机自启 | `setLoginItemSettings` | 同左（登录项） |
| 录制期间阻止休眠 | `powerSaveBlocker` | 同左 |
| 后处理单任务暂停/继续 | `ntsuspend` 原生模块 | `SIGSTOP` / `SIGCONT` |
| 崩溃后自动拉起 | 计划任务 + PowerShell 守护脚本 | `app-watchdog.cjs`（纯 Node） |
| 独立守护（父进程被杀仍能重启） | 支持 | 不支持，由 watcher 兜底 |
| 孤儿 ffmpeg 检测 | PowerShell `Get-CimInstance` | `ps -axo` |

> **孤儿 ffmpeg 检测**是什么：主程序意外退出后，它启动的 ffmpeg 子进程可能还活着、
> 还在往同一个 `.flv` 里写。如果这时程序重启去处理那场录像，两个进程同时写一个文件
> 会把文件写坏。所以动手前先查进程表，确认没有残留写入者。
> 判定要求**三个条件同时成立**才结束进程：是本应用的 ffmpeg、命令行涉及本场分片、
> 父进程归属匹配——**绝不按进程名批量杀**，避免误伤你自己的 ffmpeg。

## 字幕提取的配置要求

字幕是**可选功能**，不装也能正常录制。但它的要求和录制完全不同：录制几乎不吃资源，字幕是纯 CPU 密集任务。

### 软件环境

| 项目 | 要求 | 说明 |
|---|---|---|
| Python | **3.9+**（推荐 3.12） | 安装时务必勾选 **Add Python to PATH** |
| 依赖 | 自动安装 | `sherpa-onnx` + `numpy`，都有预编译 wheel，**不需要编译** |
| 磁盘 | 额外 ~1 GB | 模型 973 MB + venv 约 100 MB |

**Python 版本不是随便写的。** 实测 PyPI 上 `sherpa-onnx` 2.0.1 提供 Windows
`cp37`–`cp315` 共 22 个 wheel（含 `win32` / `win_amd64` / `win_arm64`），
所以 3.7 以上都能装。但 `numpy` 最新版要求 **Python ≥ 3.12**，低于此版本会
自动回退到旧版 numpy（3.9→2.0.2、3.10→2.2.6、3.11→2.4.6）。

**推荐直接装 Python 3.12**，避开版本回退带来的兼容风险。

### 硬件

| 项目 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| 内存 | 4 GB | **8 GB+** | 模型加载后常驻约 1.9 GB |
| CPU 核心 | 2 核 | **4 核+** | 线程数默认「核数−1」，核越多越快 |
| 硬盘 | 任意 | SSD | 只影响模型下载与临时音频写入 |

**没有独立显卡也能跑。** 它用的是 CPU 推理（ONNX Runtime），不需要 CUDA。

实测速度（Apple M4 Pro，4 线程）：

| 录像时长 | 耗时 | 倍速 |
|---|---|---|
| 1 分钟 | 7–9 秒 | 7–8× |
| 1 小时 | 4–8 分钟 | 约 10× |
| 4 小时 | 15–30 分钟 | 约 10× |

普通 4 核笔记本大约慢一半，仍在可接受范围。

### 内存不够会怎样

不是崩溃，而是**变慢**——Python 会开始用 swap。如果机器只有 4GB 内存，
建议：

- 不要开「录完自动转字幕」，改成录完手动点
- 转字幕时不要同时录多路

### 与录制资源的关系

| | 录制 | 字幕 |
|---|---|---|
| CPU | 几乎为 0（`-c copy` 不转码） | **4 线程跑满** |
| 内存 | ~35 MB/路 | **~1.9 GB** |
| 是否影响录制 | — | **有**，所以默认关闭且录制时让路 |

这就是为什么自动转写字幕默认关闭、而且检测到录制就排队等待。

## Windows 配置要求

### 软件环境

| 项目 | 要求 | 说明 |
|---|---|---|
| Windows | 10 / 11（64 位） | 需要 `powershell`（自带）与 `schtasks`（自带） |
| Node.js | **22.12+** | `electron@45` 的硬性要求，低于此版本 `npm install` 直接失败 |
| 磁盘剩余 | ≥ 20 GB | 依赖约 600 MB + 每场录像 |
| Python | 3.9+（**仅字幕需要**） | 不装字幕也能正常录制 |

### 硬件

录制的资源占用比想象中低，因为 **`-c copy` 只是把直播流原样写盘，不解码不转码**：

| 场景 | CPU | 内存 | 实测依据 |
|---|---|---|---|
| 录制 1 路 | 几乎为 0 | ~35 MB | ffmpeg 直拷实测 5 秒流仅 0.03s CPU、33 MB RSS |
| 录制 6 路（默认上限） | 仍然很低 | ~200 MB | 6 × 35 MB，主要是 I/O |
| Electron 界面 | 低 | ~300–500 MB | 主进程 + 渲染进程 + 后台页 |
| 转字幕（开启时） | **较高** | ~1.9 GB | 4 线程跑满，是唯一吃 CPU 的环节 |

**结论：录制本身对机器几乎没要求**，十年前的办公机也能录。真正需要留意的是两件事：

1. **磁盘写入带宽**。6 路原画同时写盘约 15–25 MB/s，机械硬盘可能吃紧，SSD 无压力。
2. **转字幕**。这是唯一 CPU 密集任务。4 核以下机器建议**不要开自动转字幕**，改成录完手动点，免得影响录制。

### 网络

| 用途 | 要求 |
|---|---|
| 拉流录制 | 稳定上行无要求，下行建议 ≥ 10 Mbps/路（按画质而定） |
| `npm install` | 需能访问 GitHub Release（国内必设镜像，见上） |
| 运行时 | 除抖音接口外无其他外网依赖，转字幕完全离线 |

### 权限

不需要管理员权限。但注意两点：

- **安装目录不要放 `C:\Program Files`**，那里写入需要提权，录像会失败。放 `D:\live-recorder` 这类普通目录。
- 首次运行 Windows 防火墙可能弹窗，**允许**即可（要访问抖音接口）。

### 与 macOS 的差异

| 能力 | Windows | macOS |
|---|---|---|
| 录制、转封装、合并、拆分 | ✅ | ✅ |
| 托盘常驻 / 关窗继续录 | ✅ | ✅（菜单栏） |
| 开机自启 | ✅ | ✅ |
| 暂停后处理任务 | ✅ 需 `ntsuspend` | ✅ 系统信号 |
| 崩溃自动拉起 | ✅ 计划任务 + PowerShell 守护 | ⚠️ 仅 watchdog 兜底 |
| 转字幕 | ✅ | ✅ |

## 快速开始

**下载项目后不能直接双击运行，必须先 `npm install`。** 因为仓库里不包含
`node_modules`（93 个源文件，约 1MB），ffmpeg 和 Electron 运行时都是
安装时按平台下载的。

前提：装 [Node.js](https://nodejs.org/) **22.12 或更高**（Windows 选 LTS 版即可）。
版本不能低：`electron@45` 的 `engines` 声明为 `>= 22.12.0`，低于此版本
`npm install` 会直接报错。装 Node 22 LTS 即可满足。

```bash
npm install     # 下载依赖 + 对应平台的 ffmpeg / Electron（约 300MB）
npm start       # 或双击启动器
```

### Windows 特别注意

`npm install` 要下载三个东西，全部走 GitHub Release，**国内直连会失败**：

| 组件 | 用途 | 未装上的后果 |
|---|---|---|
| Electron | 应用运行时 | **无法启动**（致命） |
| ffmpeg-static | 录制核心 | **无法录制**（致命） |
| ntsuspend | 单任务暂停 | 仅「暂停后处理任务」不可用，其余正常 |

所以国内网络下建议先设镜像再装：

```powershell
# PowerShell
$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
npm install --registry=https://registry.npmmirror.com
```

如果 `npm install` 报 `ffmpeg-static` 下载失败，可挂代理重试，或手动下载后
放到 `node_modules/ffmpeg-static/`（文件名需为 `ffmpeg.exe`）：

```
https://github.com/eugeneware/ffmpeg-static/releases/download/b6.1.1/ffmpeg-win32-x64.gz
```

`ntsuspend` 是可选依赖（`optionalDependencies`），它从 GitHub Release 下载预编译
的 `.node` 文件。装不上时 `npm install` **不会中断**，程序会退化为「不支持暂停
后处理任务」，启动与录制不受影响。若安装日志里有 `ntsuspend` 相关报错，可以直接
忽略。

### 启动

```bash
npm start
```

也可双击启动器：Windows 用 `启动直播录制.bat`，macOS 用 `启动直播录制.command`
（首次双击若提示「无法验证开发者」，右键 → 打开 → 打开）。macOS 细节见 `使用说明-macOS.md`。

启动器只是 `node_modules/electron/dist/electron.exe` 的快捷方式，所以**必须
先 `npm install`**，否则双击会闪退。

### 想用字幕功能（可选）

字幕需要额外的 Python 环境，同样一条命令：

```powershell
npm run transcribe:setup
```

前提是装过 Python 3.9+（安装时**勾选 Add to PATH**）。详见下文「语音转文字」。
不装也能正常录制，只是「转字幕」按钮会提示环境未安装。

打开后是个仪表盘：

- **添加监控**：粘贴直播间链接或房间号（如 `https://live.douyin.com/123456789012`），可加备注名
- **状态列**：`离线 / 直播中 / ● 录制中`，录制中实时显示时长与文件大小
- **观看**：直播中可弹独立窗口（可全屏），关闭它**不影响**录制
- **关闭窗口 = 收进托盘继续录制**；真正退出请点托盘/菜单栏图标 → 退出（会优雅封存当前录像）

## 打包

```bash
npm run dist:win    # Windows 安装包 (NSIS)
npm run dist:mac    # macOS dmg (x64 + arm64)
```

配置见 `electron-builder.json`，产物在 `dist/`。

两点注意：
- **macOS 包必须在 macOS 上打**，Windows 包同理，electron-builder 不支持交叉打包。
- `ffmpeg-static` 与 `src/transcribe/` 需要 `asarUnpack`，否则二进制/脚本被压进 asar 后无法执行。

### 打包后的数据目录

打包后代码位于 `resources/app.asar`。asar 是只读归档文件而不是目录，不能当工作目录用，
所以运行时数据（`config.json`、`logs/`、`recordings/`、`history.json`、`recording-jobs.json`、
`runtime/`）会落到真实可写目录：

| 平台 | 数据目录 |
|---|---|
| Windows | exe 所在安装目录（保持便携布局，相对 `outputDir` 仍按安装目录解析） |
| Windows（安装目录不可写，如 Program Files） | 自动退回 `%APPDATA%\直播自动录制` |
| macOS / Linux | Electron userData（macOS 为 `~/Library/Application Support/直播自动录制`） |

开发期（`npm start`）仍使用仓库根目录，行为和以前一致。也可用环境变量
`LR_ROOT=<绝对路径>` 强制指定数据目录（便携部署/多份配置隔离）。

> Windows 卸载程序会清理安装目录。若把录像留在默认位置，**卸载前请先移走录像**；
> 长期保存建议在设置里把「保存路径」改成 `D:\录像` 这类安装目录之外的绝对路径。

### 应用图标

设计是「深色圆角方形底 + 白色粗圆环 + 红色录制点」——红色录制点是录像类应用的通用符号，
配色与 `src/gui/style.css` 的暗色主题同源。

图标文件在 `build/`（即 electron-builder 的 `buildResources`）：

| 文件 | 用途 |
|---|---|
| `icon.icns` | macOS，内含 16–1024 全尺寸 |
| `icon.ico` | Windows，内含 16/24/32/48/64/128/256 |
| `icon.png` | 1024px 通用（满出血，README / 商店图等） |
| `icon-dock.png` | 1024px，符合 macOS 824/1024 内容网格，仅开发期 Dock 用 |
| `icon.svg` | 矢量源文件 |

`electron-builder.json` 里 `win.icon` / `mac.icon` / `nsis.installerIcon` 引用的是
**相对 `buildResources` 的路径**（写 `icon.ico` 而不是 `build/icon.ico`），
所以安装包、卸载器、Dock 与任务栏都会用这套图。

改设计后重新生成：

```bash
npm run icon
```

生成器在 `scripts/icon/gen-icon.py`，依赖 macOS + Google Chrome + ImageMagick。
它不是把 1024 缩到各尺寸，而是**按尺寸单独出图**：小尺寸会加粗圆环、放大红点，
否则 16px 会糊成黑点。开发期（未打包）`src/main.js` 会用 `build/icon.png` 设置窗口
图标、用 `icon-dock.png` 设置 macOS Dock 图标，避免显示 Electron 默认图标。

## 配置

界面上能改的都建议在界面改。也可以直接编辑 `config.json`，**保存后 10 秒内热重载**，无需重启。

```json
{
  "watchlist": [
    { "rid": "123456789012", "name": "示例主播" },
    { "rid": "123456789012", "name": "另一个主播", "maxSec": 3600 }
  ],
  "settings": {
    "pollIntervalSec": 3,
    "maxConcurrentRecordings": 6,
    "minFreeGB": 5,
    "autoPartMerge": true
  }
}
```

常用设置：

| 键 | 默认 | 说明 |
|---|---|---|
| `pollIntervalSec` | 3 | 轮询间隔（秒），越小开播发现越快 |
| `maxConcurrentRecordings` | 6 | 最大同时录制数 |
| `minFreeGB` | 5 | 磁盘低于此值停止开新录制 |
| `segment` | `"0"` | 分段策略。`0`=整场不分段，`90`=90 分钟，`500MB`=按大小 |
| `quality` | `highest` | 画质偏好，见下节说明 |
| `autoPartMerge` | true | 断流产生的分片最终合并回一个文件 |
| `keepDays` | 0 | 录像保留天数，0 = 永久 |
| `postConcurrency` | 2 | 后处理并发，负载高时可调回 1 |
| `autoTranscribe` | false | 录完自动转字幕（占 CPU，默认关） |
| `outputDir` | `recordings` | 录像保存位置。相对路径按安装目录解析，也可填绝对路径 |

主播项可选字段：`maxSec`（单段时长上限，主要用于测试）、`titleFilter`（只录标题匹配的场次）、`hours`（值守时段）。

### 改保存位置

界面「设置 → 保存路径」可以直接改，右边「浏览…」按钮会弹出系统的选目录对话框。
输入框下方会实时显示该目录是否可用（含剩余空间），**保存前就验证，不用等开录才发现存不进去**。

几个实际行为，提前知道能少踩坑：

| 情况 | 行为 |
|---|---|
| 目录不存在 | 自动创建（含多级） |
| 目录不可写 | 保存时直接拒绝，并说明原因（权限/只读/空间不足等） |
| 正在录制时改路径 | **不允许改**。输入框与「浏览…」按钮会置灰，并提示等录制结束 |
| 改路径后看旧录像 | 照常能看。历史记录里存了每场所属目录，不依赖当前设置 |
| 改回原来的路径 | 旧录像立刻回来 |

> 为什么录制期间干脆不让改：`ffmpeg` 的文件路径在开录那一刻就确定了，改配置不会让它跟着走。
> 允许改的话，配置里写着新目录、文件却继续落在旧目录，你按新路径去找会什么都找不到。
> 收尾（转封装）阶段同样如此，所以那段时间也算"正在录制"。

也可以在没人录的时候直接改 `config.json` 里的 `outputDir`，效果一样。

### 画质选择

`quality` 决定从平台提供的多个档位里选哪个流，**不影响是否转码**——所有档位都是直拷，
选哪档就存哪档的原始码流。

| 值 | 行为 |
|---|---|
| `highest`（出厂默认） | 原画优先，画质最好、占空间最大 |
| `lowest` | **取平台最低档，最省硬盘** |
| `FULL_HD1` / `HD1` / `SD1` / `SD2` | 指定档位 |

> 默认值只在首次运行（没有 `config.json`）时生效。已有配置会保留你之前的选择，
> 界面里改「录制画质」或直接编辑 `config.json` 都可以。

`lowest` 的取档规则：平台给了哪几档，就用其中最低的一个。例如平台同时提供
原画/蓝光/超清/高清 → 选高清；缺高清 → 选超清；只给了蓝光和原画 → 选蓝光。
**它不会回落到原画**——这正是它和「指定 `SD2`」的关键区别。

> 指定档位（如 `SD2`）在平台没提供该档时会向下找次低档；但 `SD2` 已是档位表末位，
> 无更低可落时会回落到原画。**想稳定省空间请用 `lowest`，不要用 `SD2`。**

画质下限由主播推流决定：主播本身只推高清，选 `lowest` 也只能拿到那一档。

估算占用（原画直拷，随主播码率浮动）：

| 档位 | 每小时占用 |
|---|---|
| 原画 | 约 2–4 GB |
| 最低档（约 480p） | 约 0.3–0.8 GB |

切换 `lowest` 通常能省 70–85%，但具体取决于主播推流。

## 产物

录像按房间分类：`recordings/主播名_房间号/`。同一房间复用目录，主播改名不会分裂成两个目录。

```
2026-10-26_示例主播_13-29-13_示例主题_纯享版.mp4
```

命名规则：`日期_主播名_起录时间_直播标题_纯享版.mp4`。日期时间取**起录时刻**，
标题取开录时保存的直播标题；非法字符替换，过长截短，同名自动加序号，**绝不覆盖已有文件**。

**跨午夜归属**：按上海时间判断，有两条规则——

1. **起录在 06:00 之前**：日期加「凌晨」，例如 `2026-10-27凌晨_..._03-00-00_...`
2. **跨了午夜、且结束在 09:00 之前**：归到结束日并加「凌晨」。
   例如 10-26 23:56 开始、27 日凌晨结束 → `2026-10-27凌晨_主播名_23-56-30_标题_纯享版.mp4`

文件名里的时间**始终是实际起录时刻**，录像时间轴也不受影响。其他场次按开播日期命名；
已完成的历史文件不会批量追溯改名。

## 后处理

下播后依次：转封装 → 完整性校验 →（按需）合并分片 → 超大文件拆分 → 统一命名。

- **校验通过才动源文件**。校验失败、分片损坏、文件小于 `minSizeMB` 的，一律保留原文件并在界面/日志说明。
- **合并只裁掉能确认的重放区**：靠数据包指纹唯一匹配；不能确认就保留原内容，不猜测裁剪。
- **空间不足自动等待**：处理前后都巡检剩余空间，不足时保留原片和任务，显示「等待恢复」，空间恢复后继续。
- **静音时段**：可在设置里指定每天不跑后处理的时间段（支持跨午夜）。只挡住**新任务启动**，
  已在跑的任务会完整跑完；录制本身不受影响。
- **单任务控制**：暂停/继续/取消/重试都支持。暂停是挂起同一个媒体进程保留进度，不是从头再来。

后处理使用较低的 CPU 优先级，并在拉流停滞时限制新增后处理——录制永远优先。

## 异常恢复

`recording-jobs.json` 及其 `.bak` 记录任务阶段、分片时间轴、设置和失败原因。

- 程序异常退出后，下次启动会恢复未完成任务，也会扫描符合命名规则的遗留文件
- 后处理失败**不算**完成，原因留在历史和任务面板里，重启还能看到
- 临时失败按退避自动重试；连续三次失败后可手动点「重试」
- **源文件已被删除的任务会自动结案**，不会永远卡在「等待恢复」反复重试

> 待恢复期间请保留 `recording-jobs.json*` 和原始素材。

## 历史记录

历史记录（`history.json`）保存每场的状态与文件引用。它会**自动与磁盘同步**：

- 录像被删除或过了保留期后，失效的文件引用会被清理
- 整场文件都不在了，条目**保留**但标记为「文件已删除」——它记录这场直播发生过，属日志性质
- 状态字段（完成/已修复等）不改写，保留原始记录

## 主播分组与主页导入

- 按公司折叠主播列表；可新建、改名、批量移动。折叠时仍显示录制、暂停、异常和主页监控数量
- 删除公司只把主播移回「未分组」，**不删监控、不删录像**
- 搜索匹配主播名/房间号/标题/公司；搜索期间自动展开匹配组，清除搜索恢复原折叠状态
- 支持导入个人主页链接：已识别房间号的直接秒级监控；离线导入则等首次开播识别，
  成功后永久转为房间号监控。重复房间自动合并为一个任务

## 语音转文字（本地，完全离线）

把录好的视频转成文字稿和字幕。**全程不联网**，音频不出本机——除了首次下载模型，运行时不产生任何网络请求。

### 为什么是这个方案

选型的关键不是「哪个最准」，而是「换台电脑还能不能跑」。调研过的选项及排除原因：

| 方案 | 结论 |
|---|---|
| **sherpa-onnx + Qwen3-ASR** | ✅ 采用。Apache-2.0，有 Windows/macOS/Linux 全平台预编译包 |
| 官方 `qwen-asr`（PyTorch） | ❌ 官方只支持 CUDA，Mac 和纯 CPU 属未支持状态 |
| `qwen3-asr-rs`（Rust） | ❌ 无预编译二进制，必须装 Rust 工具链自行编译 |
| SenseVoice（阿里开源） | ❌ 只支持中/英/粤/日/韩，**不覆盖北方官话细分口音**，会强行转成普通话 |
| 云端 API（阿里百炼等） | ❌ 需上传录音，不接受 |

**方言覆盖**：支持 31 种语言 + 22 种中文方言，覆盖东北、四川、河南、山东、陕西、山西、河北、安徽、湖北、湖南、江西、浙江、江苏、云南、贵州、甘肃、宁夏、福建等地方言，以及吴语、闽南语、粤语（香港/广东）。

方言识别会**保留原词**，不会洗成普通话。实测粤语输出「揾到」「喺」「俾我哋」均保留原字。

### 安装（Windows / macOS 通用）


安装过程**不污染系统 Python**：所有依赖装在 `runtime/asr/venv/`，删掉整个 `runtime/` 即可完全卸载。

### 使用

```bash
npm run transcribe -- "recordings/主播名/某场.mp4"        # 单个文件
npm run transcribe -- recordings/主播名 --all             # 整个目录（递归）
npm run transcribe -- 某场.mp4 --hotwords "商品名,主播名"  # 带热词，提升专名识别
```

产物与视频同目录：`某场.srt`（字幕）+ `某场.txt`（纯文本）。

常用选项：

| 选项 | 说明 |
|---|---|
| `--all` | 递归处理子目录 |
| `--hotwords "词1,词2"` | 热词偏置，商品名/人名/口播术语建议填 |
| `--no-auto-hotwords` | 关闭自动热词（默认会从主播名推导） |
| `--threads N` | 线程数，默认 CPU 核数减一 |
| `--max-speech N` | 单段最长秒数，默认 15 |
| `--no-srt` / `--no-txt` | 只要其中一种输出 |
| `--keep-audio` | 保留抽取的临时 wav，便于排查识别质量 |

### 硬件与速度

**纯 CPU 即可，不需要显卡。** 实测（Apple M4 Pro，4 线程，0.6B int8）：

| 指标 | 数值 |
|---|---|
| 内存占用 | 约 1.9 GB |
| 磁盘 | 模型 950 MB |
| 识别速度 | **16–31 倍实时**（4 小时直播约 8–15 分钟转完） |
| 模型加载 | 约 1.3 秒/次 |

普通笔记本（4 核 8GB）也能跑，速度大约减半，仍在可接受范围。

### 什么时候开始转写

有两条路径，互不冲突：

**一、自动（默认关闭）**

设置里勾选「录完自动转字幕」后，每场录像收尾完成会自动转写。开启方式：

```bash
# 界面：设置 → 录完自动转字幕
# 或直接改 config.json
"autoTranscribe": true
```

自动转写有三条保护，都是为了让字幕不影响录像：

| 保护 | 行为 |
|---|---|
| 录制期间让路 | 有任务在录时排队等待（每 30 秒检查一次），不跟直拷/转封装抢 CPU |
| 失败隔离 | 转写失败只记录在转写条目上，**不改录像的 status/error**，录像已落盘就是成功的 |
| 不阻塞收尾 | 独立队列，不塞进后处理队列，避免界面「正在收尾」卡住几分钟 |

**二、手动（随时随地）**

录像浏览窗口里，每个视频旁边有「转字幕」按钮。适合补跑历史录像，或自动转写失败后重试。

也可以走命令行，适合批量：

```bash
npm run transcribe -- recordings/主播名 --all
```

### 转写耗时参考

| 录像时长 | 大约耗时（4 线程 CPU） |
|---|---|
| 1 小时 | 4–8 分钟 |
| 4 小时 | 15–30 分钟 |

这是 CPU 密集任务。如果机器同时在录多路，自动转写会一直等到录制空闲才开始——这是刻意的，宁可晚转也不要影响录制。

### 热词：默认自动，但必须克制

不传 `--hotwords` 时，工具会自动从**文件名里的主播名**和 **history.json 的主播名**推导热词。
只取主播名（含括号内别名），不取直播标题——标题往往是话题句而非专名。

**这不是可选的优化，是踩过坑的结论。** 同一段 60 秒语速密集、专名频繁的音频实测：

| 热词数 | 结果 |
|---|---|
| 0 个 | 同一人物名出现三种不同写法 |
| **2 个** | 人名写法全部统一，还额外修正出一处漏识别的词 |
| 5 个 | 第一段直接输出成热词串本身，**真实内容丢失** |
| 10 个 | 出现 `system` 这样的垃圾输出 |

所以热词上限硬编码为 4 个，且过滤规则很严：

- 含 `#`、逗号、句号、问号的丢弃（曾导致模型把话题标签连同 `#` 一起吐进正文）
- `test`、`题目`、`纯享版`、纯日期/时间等占位内容丢弃
- **括号允许**：`某某说手机（别名）` 这类带别名的主播名必须保留，否则整个名字会被拒
- `Mate70Pro` 这类带数字的型号保留；纯小写字母单词丢弃

想手动覆盖就传 `--hotwords`，两者不会叠加。

### 几个实现上的坑（改代码前必读）

- **必须切片再识别**。Qwen3-ASR 单次可处理的 token 数受 `max_total_len` 限制。实测把 272 秒音频整段送入，会因音频占位符（3541 个）超出上限被截断，**输出为空**且只有一行告警。所以流程固定为「VAD 切成 ≤15 秒语音段 → 逐段识别」。
- **必须分块喂 VAD**。`VoiceActivityDetector` 内部缓冲固定，一次性 `accept_waveform` 整段长音频会覆盖尚未取走的结果。代码按 512 采样点（32ms）逐块喂入。
- **相邻短段要合并**。VAD 按静音切得很细，逐段识别会把一句话拆成多条字幕。`merge_short()` 在「间隔 ≤0.35 秒且合并后 ≤15 秒」时并起来。
- **音频规格固定为 16kHz / 单声道 / 16-bit PCM**，由 ffmpeg 统一转好再交给 Python。这样 Python 侧不需要 soundfile/librosa，Windows 上少一类编译问题。

### 限制

- **0.6B 是精度与体积的折中**。1.7B 更准（WER 3.6% vs 5.2%），但 ONNX 版本需自行导出，且内存约 4.6 GB。当前选用 0.6B 是为了让普通机器也能跑。
- **没有手动方言开关**。模型自动判别语种/方言，不能强制指定某一地区口音。若某场识别偏差大，优先试 `--hotwords` 补专名。
- **不产出逐字时间戳**。时间戳精度到「句」（VAD 段边界），不是逐字对齐。

## 说明与限制

- **完整性检查耗时**取决于录像长度和硬件，因为它要完整解码一遍。检测失败时优先保留源文件。
- **拉流停滞**：读取超时或约 15 秒没有媒体进度时会结束卡住的进程，按重连退避续录。
- **开播前 1~3 秒画面物理上拿不到**（数据还没发出来），调小轮询间隔能压缩这个窗口。
- **硬崩溃/断电**可能留下损坏尾部。自动恢复只发布通过检查的产物，无法确认完整时保留原件并提示。
- **帧率/画质上限** = 主播推流质量 + 平台网页端给出的档位，程序不能凭空提升；
  想要更低画质可以设 `quality: lowest`，但不可能低于平台提供的最低档。
- 个别主播可能遇到「原画登录墙」。
- 请仅用于个人观看存档，勿二次传播。
